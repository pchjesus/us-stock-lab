# G1-C2 금융 migration 리허설 — 운영 적용 NO-GO

이 문서는 실행 승인이나 운영 배포 스크립트가 아니다. 대상은 Supabase 프로젝트 `vveljtqmujdzkzmoncjx`, migration 004~007이다. 운영 DDL/DML, repair, API 설정 변경, Cron, Pages는 G1-C2에서 수행하지 않았다. 운영 적용은 별도 명시적 승인과 아래 차단 요인의 해소가 모두 필요하다.

## 검증된 사실

- `python3 scripts/rehearse-cli-history.py /absolute/path/to/supabase`는 검증된 Linux amd64 Supabase CLI 2.122.0 바이너리만 받아 임의 이름의 `postgres:17` 컨테이너를 `--network none --pull=never`로 실행한다. CLI와 DB는 같은 컨테이너 안에서만 통신하며 운영 연결 인자는 받지 않는다. 테스트는 모의 Auth와 합성 계좌만 생성하고 컨테이너를 정리한다. CLI 배포 파일의 SHA256은 `59ed066847b98d7461c60e9109d40cab6b9756177ce06ebb05b51338519f5136`이다.
- 모사 DB에서 공식 CLI `db push --skip-vault --dry-run`은 004~007만 출력하고 테스트한 상태를 변경하지 않았다. 이 결과는 운영 DB에서의 동작이나 모든 부작용의 부재를 증명하지 않는다. CLI 도움말은 `db push`가 기본적으로 Vault 설정을 먼저 갱신할 수 있다고 밝힌다.
- 004·005·007 본문에 각각 임시 실패를 주입한 경우 앞선 성공 migration만 이력과 스키마에 남았다. 005 또는 007이 실패한 상태에서 인증 역할의 `manual_snapshot()`을 호출하면 계좌가 실제 생성됐다. paper 계좌와 합성 수기 원장의 잔액 합계는 일치했다. 오류를 제거하고 재실행하면 완료됐고, 완료 후 CLI 재실행은 이력상 no-op이었다. 이는 실제 운영에서의 자동 재시도 지침이 아니다.
- 004 본문 커밋 뒤 history INSERT에 오류를 주입하면 004 스키마와 인증 역할 RPC 권한은 남았지만 004 이력은 없었다. 실패 트리거를 제거한 뒤 일반 CLI 재시도는 중복 객체로 실패했고 이력은 여전히 없었다. 이 상태는 자동 repair 또는 재실행 대상이 아니다.
- 정상 적용 뒤 테스트한 금융 RPC 9개는 anon EXECUTE 불가, authenticated EXECUTE 가능이며 수기·배당 public 테이블에 RLS가 활성화됐다. 이는 운영 인증 사용자 격리나 모든 API 경로 검증이 아니다. 기존 격리 금융 테스트의 더 넓은 검증과 구분한다.
- 추가로, 원본을 변경하지 않고 메모리 사본의 최상위 `BEGIN`/`COMMIT`을 제거한 실험에서 004~007과 수기 모의 history를 하나의 PostgreSQL 트랜잭션으로 묶었다. 별도 세션에서 004·006 중간 RPC/history는 보이지 않았고 paper 잔액은 읽혔다. 004·005·007 전 실패와 007 history INSERT 실패에서 전체가 롤백됐다. 이는 공식 CLI 배포 또는 운영 수기 history 변경의 승인·검증이 아니다. 상세: `docs/finance/G1_C2_DEPLOYMENT_GATE.md`.

## 대안 및 차단 요인

1. **A — 원자적 적용:** 원본 004~007에 개별 `BEGIN`/`COMMIT`이 있고 CLI가 별도 history 기록 시 실패할 수 있음을 재현했다. 기존 파일과 공식 CLI를 그대로 사용하는 전체 원자적 적용은 검증되지 않았다. SQL을 변형하거나 history를 수기로 쓰는 별도 도구는 승인된 공식 경로로 간주하지 않는다.
2. **B — Data API 중지:** [공식 문서](https://supabase.com/docs/guides/api/securing-your-api)는 Data API 비활성화 시 자동 REST 엔드포인트를 끈다고 설명한다. 이는 paper API도 일시 중단하고, 직접 DB 등 모든 경로를 차단한다는 증거가 아니다. 이 프로젝트에서 설정 가능 여부, 전파 지연, 기존 세션, 실패 후 유지 및 재개는 검증하지 않았다. 운영 설정을 변경하지 않았다.
3. **C — 배포 게이트:** 마이그레이션 중간 및 실패 후에도 모든 외부 인증 경로를 차단하면서 paper 기능을 보존하는 게이트는 아직 구현·검증되지 않았다. UI 숨김이나 사용자 수 0건은 보안 경계가 아니다.

따라서 현 단계에서 어느 대안도 운영용으로 승인하지 않는다. 공식적으로 지원되는 차단 경로와 접근 경로 전수 확인, 실패 후 닫힘 상태, paper 영향 및 재개 동작을 격리 환경에서 검증해야 한다. 실제 운영 `migration list`와 `db push --dry-run`도 NOT VERIFIED다. 임의의 운영 연결 정보나 다른 쓰기 명령으로 우회하지 않는다.

## 운영 실패 시 중단 원칙

차단 경로를 검증하고 별도 운영 승인을 받기 전에는 배포를 시작하지 않는다. 향후 승인된 배포 중 오류나 연결 손실이 발생하면 **후속 실행·재시도·재개를 중단**하고, 검증된 차단 상태를 유지한 채 정확한 프로젝트 ID와 migration 이력, 실제 객체·함수·권한·RLS·원장 불변식을 읽기 전용으로 비교한다. history가 없더라도 SQL이 커밋됐을 수 있다. 이력만 보고 SQL을 재실행하거나 `migration repair`를 일괄 적용하지 않는다. 복구 계획은 실제 상태별로 별도 검토·승인하고, 전체 검증 후에만 차단 해제를 검토한다. 현재는 그 실행 수단과 차단 해제 조건이 완성되지 않았다.
